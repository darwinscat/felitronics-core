# THE SYSTEM-libm MANIFEST — every call to a system transcendental OUTSIDE the deterministic zone.
# Checked by tools/lint/check-det-math.mjs; read that file first for what the zone is and why this list
# is per-FILE rather than per-call-site.
#
# Format:   <path>  [<fn>*<count> ...]  <disposition>  <reason>
#
# The bracketed multiset is the exact set of governed functions the file calls. It is what makes this a
# gate rather than a comment: a call added, removed, or swapped for a different function moves the line
# and the build goes red until somebody re-reads the file. A line move or a whitespace change does not.
#
# Dispositions, and what each one CLAIMS:
#   retain-rt        the result is a shipped product's audio. Changing it changes TabbyEQ's or OrbitCab's
#                    sound, so it is the owner's decision and not a technical edit. RT modules may only
#                    ever gain an ADDITIVE deterministic path through the SystemMath/DetMath type policy.
#   retain-local     the result never leaves the machine that computed it — a GUI curve, a pixel mapping,
#                    a display ballistic. Nobody diffs it against another row because nobody can.
#   retain-offline   offline, and the result DOES leave (a written file, a measured IR), but it is compared
#                    with a tolerance rather than byte for byte, and no parity harness reads it.
#   owner-decision   it crosses a boundary AND it is shipped bits. Both things are true, so it is listed
#                    here rather than quietly converted or quietly ignored.
#
# WHAT THIS MANIFEST DOES NOT CLAIM. It records where the calls are and what they are for. It does not
# claim to know their CADENCE: whether a call runs once per prepare() or once per sample is a property of
# the caller's loop, and no text scanner can see through a template, a helper or a call graph to decide it.
# Where cadence is the reason for a disposition it is written into the reason in words, having been read.

# --- eq: the biggest group, and all of it is coefficient design for shipped filters ---
modules/eq/include/felitronics/eq/EqBand.h  [abs*1 polar*1 sin*1]  retain-rt  Butterworth Q design and the z^-1 phasor for a band's response. std::polar is cos+sin in disguise, which is why the lint governs it
modules/eq/include/felitronics/eq/EqEngine.h  [abs*3 log10*2]  retain-rt  the composite magnitude response in dB, for the curve the user sees and for the engine's own fitting
modules/eq/include/felitronics/eq/MatchedBiquad.h  [abs*25 cos*10 cosh*1 exp*7 log10*1 polar*1 pow*9 sin*12 sqrt*19 tan*3]  retain-rt  TabbyEQ's filter design, all of it: matched-pole placement, shelf solving, notch cascades, bandpass cascades. These transcendentals ARE the coefficients, and the coefficients ARE the product's sound. The 25 std::abs are a MIX — most are scalar magnitude on a coefficient, and only the ones taking a std::complex are hypot; the 19 std::sqrt include complex square roots in the pole solver (:400, :641), which scalar IEEE exactness does not cover
modules/eq/include/felitronics/eq/MultibandSplitter.h  [pow*1]  retain-rt  the default band frequencies, laid out geometrically

# --- limiter / saturation: shipped audio, some of it per sample ---
modules/limiter/include/felitronics/limiter/TruePeakLimiter.h  [dbToGain()*3 exp*1 gainToDb()*2 log*1]  retain-rt  the release coefficient. NOTE the limiter's other libm reach is through core::gainToDb and core::dbToGain INSIDE its oversampled per-sample loop — a carrier, not a direct call, and the reason gainToDb was not converted in place. K13 added dbToGain twice in apply(): the clip level and the knee half-width, COEFFICIENTS computed once per parameter change, which is the same consumer class as every other gain coefficient here and not a reported value. The clipper's own reported dB goes through gainToDbDet instead, because that one crosses the ABI and an ulp there moves a histogram bin
